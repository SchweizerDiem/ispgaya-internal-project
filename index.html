Local Weather

Uma plataforma de agregação de APIs meteorológicas nacionais. Em vez de recorrer a um serviço global genérico, o Local Weather fala diretamente com a agência oficial de cada país — IPMA, AEMET, CWA — e cai para o Open-Meteo onde nenhuma delas cobre.

01

Visão Geral

O utilizador que consulta habitualmente a agência do seu país de residência confronta-se, ao precisar de previsões para outro país, com a necessidade de recorrer a serviços globais genéricos e menos precisos — por desconhecer a existência das agências nacionais de cada região, ou por as encontrar redigidas na língua local. O Local Weather resolve isto centralizando o acesso a quatro fornecedores meteorológicos por trás de uma interface única, sem perder a precisão inerente a cada fonte local.

02

Arquitetura

Arquitetura cliente-servidor em três camadas lógicas. O browser nunca fala diretamente com os fornecedores externos — evita problemas de CORS e mantém as chaves de API fora do cliente.

Camadas do backend

models/
Esquemas Pydantic por fornecedor — sem tentativa de unificação; a diferença entre APIs é preservada, não escondida.
providers/
Toda a comunicação HTTP externa. Cada adaptador expõe apenas funções assíncronas de alto nível (ex. fetch_daily(municipio_id)).
routers/
Endpoints FastAPI, validação Pydantic, chamada aos adaptadores. Nunca fazem chamadas HTTP diretas.

Porquê o padrão Adapter

Cada fornecedor tem a sua própria lógica de autenticação, formato de resposta e codificação de texto. O Adapter isola essa especificidade num módulo substituível — adicionar a Météo-France ou o DWD amanhã não implica tocar em nenhum módulo existente, apenas escrever um novo adaptador.

03

Fornecedores

Quatro fontes de dados, quatro contratos completamente diferentes.

🇵🇹

IPMA

Instituto Português do Mar e da Atmosfera

  • Sem autenticação
  • Previsão diária · 3 dias
  • Sem condições atuais
  • Identificação por globalIdLocal

Catálogo estático de cidades (capitais de distrito, Açores, Madeira) mantido em memória — pesquisa instantânea, sem chamada de rede extra.

🇪🇸

AEMET

Agencia Estatal de Meteorología

  • Requer chave de API
  • Diária · 7 dias / Horária · 48h
  • Sem condições atuais
  • Identificação por código INE

O fornecedor mais complexo: fluxo de dois pedidos HTTP e respostas codificadas em ISO-8859-1, não UTF-8. Ver Registo de Ocorrências.

🇹🇼

CWA

Central Weather Administration, Taiwan

  • Requer chave de API
  • Atuais + 36h + Diária · 7 dias
  • 22 condados/cidades
  • Vento em classes textuais (mandarim)

Datasets individuais por condado (ex. F-D0047-063 para Taipei) — não existe um identificador global funcional.

🌍

Open-Meteo

Serviço agregador global de código aberto

  • Sem autenticação (até 10.000 chamadas/dia)
  • Atuais + Horária + Diária · 16 dias
  • 15 países no âmbito do projeto
  • Licença CC BY 4.0

O adaptador mais simples: pedido único, sem fluxo multi-fase, sem anomalias de codificação. Serviu de prova de conceito da arquitetura.

06

Stack Tecnológico

Backend

  • FastAPI — framework assíncrono, documentação OpenAPI automática
  • Pydantic — validação de esquemas tipificados (núcleo em Rust desde a v2)
  • httpx.AsyncClient — chamadas HTTP paralelas com asyncio.gather()
  • pytest + pytest-asyncio — 196 testes, modo automático

Frontend

  • React — Context API para unidades e idioma (sem Redux)
  • MUI X Charts — visualização horária e diária de temperatura
  • localStorage — histórico de pesquisas, preferências
  • Nominatim (OpenStreetMap) — geocodificação inversa via proxy

07

Registo de Ocorrências

Os quatro problemas técnicos que mais tempo consumiram durante a integração — e como foram resolvidos.

AEMET

Codificação ISO-8859-1

Erro de parsing JSON que só ocorria para localidades com caracteres especiais espanhóis. Causa: a AEMET codifica as respostas em ISO-8859-1, enquanto o httpx assume UTF-8 por omissão — o byte 0xBA (º) corrompia o JSON antes do parsing.

Resolução: ler r.content em bruto e descodificar explicitamente com .decode("latin-1") antes de json.loads().

CWA

Identificador de dataset inválido

A documentação referia F-D0047-093 como identificador global de previsão a 7 dias. Devolvia HTTP 404 de forma consistente — os dados estão, na realidade, organizados por condado, cada um com o seu próprio identificador.

Resolução: registo local CWA_LOCATIONS com o identificador correto para cada um dos 22 condados/cidades.

CORS

Geocodificação inversa via Nominatim

O Nominatim não envia o cabeçalho Access-Control-Allow-Origin, impedindo chamadas diretas a partir do browser para a funcionalidade de geolocalização automática.

Resolução: endpoint proxy GET /geo/reverse no backend, que chama o Nominatim do lado do servidor.

Testes

Mocking assíncrono

Substituir httpx.AsyncClient por AsyncMock produzia 'coroutine' object has no attribute 'get' — r.json() e r.raise_for_status() são chamados de forma síncrona, mesmo com cliente assíncrono.

Resolução: MagicMock para esses dois métodos; AsyncMock apenas onde há await real. Regra geral adotada: fazer patch onde a função é usada, não onde é definida.

08

Trabalho Futuro

Direções identificadas, por ordem decrescente de impacto arquitetural.

  1. Endpoint unificado — GET /weather/city?city={nome} com seleção automática de fornecedor no backend, completando o padrão Aggregator.
  2. Caching com TTL — cache em memória diferenciado por tipo de dado (10 min para condições atuais, 3h para previsão diária), protegendo as chaves de API.
  3. Expansão de fornecedores — candidatos: DWD (Alemanha), FMI (Finlândia), INMET (Brasil), Met Office (Reino Unido).
  4. Dashboard de saúde dos fornecedores — GET /health/providers com tempo de resposta e deteção precoce de alterações de contrato.
  5. Comparação de cidades — duas localizações lado a lado, cada uma pelo seu próprio fornecedor.
  6. Análise de precisão histórica — comparação com a reanálise ERA5 do Open-Meteo desde 1940.
  7. Progressive Web App — service worker para consulta offline da última previsão obtida.
